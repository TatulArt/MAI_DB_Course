# Обоснование 3НФ

**Условия.** 1НФ: значения атомарны, нет повторяющихся групп. 2НФ: неключевые поля зависят от всего ключа, а не от его части. 3НФ: неключевые поля зависят только от ключа, а не друг от друга (нет транзитивных зависимостей).

Во всех таблицах первичный ключ — одиночный суррогатный `id`, поэтому частичных зависимостей нет и 2НФ выполняется автоматически. Значения во всех столбцах атомарны, групп-повторов нет (несколько товаров заказа — отдельные строки `order_items`), поэтому 1НФ выполнена.

## 3НФ по таблицам

| Таблица | Почему нет транзитивных зависимостей |
|---|---|
| `customers` | имя, email, телефон описывают только клиента |
| `categories` | единственный атрибут — название |
| `products` | вместо названия категории хранится `category_id`; название берётся из `categories` |
| `orders` | вместо данных клиента хранится `customer_id` |
| `order_items` | нет названия товара и данных заказа — только ссылки и количество |
| `payments` | факты о платеже; данные заказа берутся по `order_id` |
| `order_status_history` | факты о смене статуса; данные заказа берутся по `order_id` |

## Что вынесено при нормализации

Если бы таблица была плоской `заказ(клиент, email, товар, категория, цена, ...)`, данные клиентов, товаров и категорий дублировались бы в каждой строке и расходились при изменении. Поэтому они разнесены по отдельным таблицам и связаны внешними ключами.

## Спорные места

- **`order_items.unit_price`** выглядит как дубль `products.price`, но это не так: цена товара меняется со временем, а `unit_price` фиксирует цену в момент покупки. Это самостоятельный факт о позиции заказа, зависящий от всего её ключа.
- **`orders.status` и `order_status_history`:** текущий статус совпадает с последней записью истории. Это контролируемая денормализация ради быстрых запросов; согласованность поддерживается при вставке данных, триггера нет.
